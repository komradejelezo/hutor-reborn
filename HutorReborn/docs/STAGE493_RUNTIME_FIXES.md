# Этап 4.9.3 — фактический запуск, двери и жизнь деревни

Основа: `main`, коммит `9c8c14cb8dcf909e5410e7d7a1bcf73ffe038871`, уже содержащий объединённые PR #15 и #16. Рабочая ветка: `codex/stage493-runtime-fixes`. PR предназначен для проверки, без автоматического объединения.

Исправлены две установленные технические причины. Все шесть существующих интерьеров полноценны; повторно создавать или перестраивать их не потребовалось. Из прежних файлов изменены только `scripts/interiors/interior_travel.gd` и `scripts/life/village_life.gd`: всего 13 добавленных строк. Ещё 1299 исходных файлов сохранены побайтно, включая сцены, настройки проекта, изображения, портреты, анимации, расписания, освещение и диалоги.

Материалы проверки: [deliverables/Stage493](../../deliverables/Stage493), [машиночитаемый результат](../../deliverables/Stage493/validation.json). Видео и PNG сняты с настоящего окна игры, без перерисовки.

## 1. Почему вместо входа открывалась карточка

**Причина установлена и воспроизведена.** При обычном запуске настроенной главной сцены карта уже присутствует в `SceneTree.root` и `current_scene` к моменту выполнения `_ready()` служб `InteriorTravel` и `VillageLife`. Они подписывались только на последующие `root.child_entered_tree`. Первую карту подписка не видела.

Из-за этого `InteriorTravel._bind_village()` не вызывался: шесть `InteriorDoor` не создавались, старые информационные точки не переносились во дворы. Изменённый ранее приоритет двери здесь помочь не мог — самой двери в системе не было. Ганс выбирал прежнюю карточку здания.

В исходной версии изолированно запущен именно `main` указанного коммита. Ганс дошёл до дома старосты настоящими WASD; настоящее E открыло карточку «Дом старосты», оставив Ганса на улице. См. [карточку до исправления](../../deliverables/Stage493/before/before-elder-info-card.png), [подсказку до исправления](../../deliverables/Stage493/before/before-elder-prompt.png). Диагностика порядка запуска: `before/bootstrap-before.log`. Временные диагностические сообщения в игровой код не включены.

**Исправление:** `interior_travel.gd`, `_ready()`, строки 39–41: после подписки обработать уже существующую `current_scene` тем же `_root_added()`. Существующая отложенная привязка и защита `interior_doors_bound` предотвращают повторную регистрацию. Координаты, коллизии, реестр интерьеров и правила приоритета из #15 сохранены.

**Почему прежние проверки пропускали ошибку:** тесты с `--script` создавали карту после запуска autoload. Сигнал в таком порядке приходил. Новый тест запускает настроенный проект без `--script`; на исходном `main` результат 1/6, после исправления 6/6. Один лишь успешный импорт не использовался как подтверждение входов.

**Фактическая проверка:** сначала выполнен вход/выход трактира, затем остальных пяти домов. Ганс физически дошёл до каждой двери; проверены точные подсказки `E — Войти` / `E — Выйти`, настоящая смена `current_scene`, движение внутри, возврат к соответствующей двери, восстановление управления и масштаба камеры. Карточка не открывалась. Трактир дополнительно пройден повторно после окончательной правки скорости NPC. Остальные пять оконных проходов выполнены после исправления запуска, перед независимой правкой скорости; окончательный код всех дверей повторно проверен программно.

Существующий переход снимает прежнюю сцену с дерева, подключает отдельную сцену помещения и назначает `get_tree().current_scene = destination` (`interior_travel.gd`, `_travel()`). Это реальные отдельные игровые сцены. Комнаты и наружная карта кэшируются прежней системой; тот же экземпляр Ганса переносится между ними. Сохраняются время и девять экземпляров жителей. Внутренний масштаб 1.3, наружный восстанавливается из сохранённого состояния.

## 3. Жители не входили в дома

**Причина установлена:** та же потеря события начальной карты в `VillageLife._ready()`. `_bootstrap()` не выполнялся; не создавались состояния распорядка, часы и шлюзы переходов. Жители оставались в старых уличных маршрутах, хотя профили распорядка и полноценные комнаты уже существовали.

**Исправление:** `village_life.gd`, `_ready()`, строки 45–47: обработка имеющейся карты после подписки. `_bootstrap()` уже защищён флагом `initialized`, поэтому повторные события не создают копий жителей. Существующие ID, домашние сцены, шлюзы, расписания и материализация сохранены.

**В настоящей игре:** ускорение только клавишей F7; наблюдались возвращение работников, подход брата травницы к дому, исчезновение с улицы. Ганс заранее вошёл в дом травницы и освободил внутреннюю точку входа. В комнате появился тот же экземпляр брата, дошёл до бытового места. E открыл диалог с портретом; после Esc он вернулся к занятию. См. [появление внутри](../../deliverables/Stage493/screenshots/brother-home-arrival.png), [диалог](../../deliverables/Stage493/screenshots/returned-resident-dialogue.png).

Вечером в 19:32 зафиксировано логическое нахождение всех девяти ID в собственных домах: [all-residents-home.json](../../deliverables/Stage493/all-residents-home.json). Это наблюдение состояний, а не одновременное визуальное присутствие девяти жителей: при Гансе снаружи неактивные интерьеры симулируются виртуально. Непосредственно внутри при возвращении наблюдался брат; поочерёдное визуальное сопровождение каждого из девяти в этот вечер не выполнялось. Программная проверка жизненного цикла проверяет остальных и сохранение девяти экземпляров между комнатами.

## 4. Работники не уходили на лесозаготовки

**Первичная причина:** расписание не запускалось из-за ошибки инициализации. Точки выхода/возврата и существующий переход `boundary_out` / `logging` / `boundary_in` уже реализованы в #16; заново создавать их не требовалось.

**Дополнительная причина, найденная в настоящей игре после починки старта:** если утренний уход происходит виртуально, пока Ганс внутри, первое физическое появление работника может оказаться вечерним возвращением. В `_materialize()` для `boundary_in/out` не создавалось отдельное runtime-определение. `actor.definition` ещё ссылалось на `record.original`. Обработчик F7 `_speed_changed()` записывал ускоренную скорость прямо в исходный ресурс. После возврата к x1 скорость не восстанавливалась; появлялись чрезмерно быстрые перемещения и накопительное умножение.

Регрессия на исходном `main`: базовые 36/37 превратились в 518400/4440 после ускорения/сброса. Это результат специально изолированного программного теста, не штатные значения игры. В промежуточном оконном прохождении дополнительно наблюдалась фактическая скорость движения 960 при часах x1.

**Исправление:** `village_life.gd`, `_materialize()`, строки 316–320: создать runtime-копию определения **до** `reparent` возвращающегося тела и обновить ссылку SpriteFrames через существующую библиотеку. Картинки/анимации не заменяются. `_speed_changed()`, строки 504–505: защитное копирование при обнаружении ссылки на исходный ресурс. Дальше применяется прежний расчёт скорости.

**В настоящей игре после исправления:** Ганс провёл первое утро в трактире. Оба работника ушли виртуально, не успев пройти физически ни одного шага (`distance_walked < .1`). Он вышел и дождался их вечернего возвращения у северной тропы. F7 возвратил x1: исходные и runtime-скорости остались 36/37, `source_alias=false`. Затем на следующее утро оба тех же экземпляра физически прошли северный маршрут, покинули видимую карту и получили `scene=logging`, без пересоздания.

Видео: [вечернее возвращение](../../deliverables/Stage493/videos/workers-evening.mp4), [утренний уход](../../deliverables/Stage493/videos/workers-morning.mp4). Уход виден примерно на 32-й секунде утренней записи; [кадр](../../deliverables/Stage493/screenshots/workers-morning-departure.png). При x30 шаги обновляются быстрее — это штатное ускорение F7. Наблюдение подтверждено позициями, событиями и постоянными ID в протоколе. Локация лесозаготовок не создавалась.

## 5. Застревание рядом с Гансом

Отдельную постоянную ошибку обхода после корректного запуска и исправления скорости воспроизвести не удалось. Нельзя приписывать всем прежним остановкам одну доказанную причину. Установлено, что исходная игра не включала требуемый распорядок, а некорректное общее определение могло оставлять скорости неверными после ускорения.

Проверена действующая система из #16: ограниченный динамический поиск AStarGrid2D в `scripts/npc/navigation_service.gd`, обработка препятствий в `scripts/npc/npc.gd`, пересчёт/ожидание недоступной цели. NavigationAgent2D здесь не используется. NPC имеют маску 7 (мир 1, Ганс 2, жители 4); маска Ганса 1 сохранена. Коллизии не отключались.

В настоящем окне Ганс **три раза** вставал WASD на ближайший маршрут работника. Проверка ждала подхода NPC ближе 45 px и последующего прогресса более 12 px при неизменной позиции Ганса. Все три случая пройдены; снимки `hans-block-1/2/3.png`. Программные 14 проверок дополнительно покрывают закрытую цель, ограниченное число попыток и продолжение после освобождения препятствия; суточный прогон проверяет расстояния между жителями и бюджет поиска.

Алгоритм навигации не переписывался без новой воспроизводимой ошибки. Эти проверки не доказывают отсутствие любой возможной блокировки толпой. В полностью перекрытом узком проходе ожидание до освобождения допустимо.

## 6. Структура, актуальные ресурсы и портреты

В проверяемом репозитории один действующий корень Godot: `HutorReborn/project.godot`. Активной вложенной `hutor-reborn-main` внутри него нет. Найдены и проверены 1842 буквальные ссылки `res://` в игровых скриптах, сценах, данных и ресурсах: отсутствующих путей нет. Дубликатов `.uid` и `class_name` не обнаружено. Проверка не доказывает корректность произвольных динамически собираемых строк, поэтому отдельно проверены реальные загрузки.

Ничего из пользовательских копий не удалялось. Локальная папка, после удаления которой у пользователя появились портреты, здесь недоступна; её конкретный конфликт UID/классов/импорта исторически установить нельзя. В текущей игре правильный портрет в настоящем диалоге показан, все исходные портреты побайтно сохранены.

При загрузке ZIP GitHub нормальна внешняя оболочка `hutor-reborn-main/HutorReborn/project.godot`. Открывать следует этот `project.godot`. Не распаковывать целый репозиторий внутрь уже открытого `HutorReborn/` (`res://`). Если резервная копия действительно нужна внутри корня, сначала проверить её ссылки/использование и пометить отдельной `.gdignore` либо хранить за пределами проекта. Инструмент `tools/verify_project_layout.py` только сообщает проблемы, не удаляет файлы. Его детектор отдельно проверен на временных примерах вложенного проекта и дубликата UID.

## 7. Что действительно проверено

Движок: официальный Godot **4.6.3**, Linux/Xorg, Compatibility, Mesa llvmpipe. В консоли оконной игры нет ошибок скриптов, загрузки и исполнения. Есть предупреждение драйвера об отсутствии переключения V-Sync; оно не связано с игровыми системами.

**Оконное прохождение автоматизировано через настоящие события клавиатуры X11 XTest.** Игра стартовала обычной настроенной главной сценой, без `--script`. Драйвер не телепортировал Ганса/NPC, не вызывал переходы программно и не переводил часы методом `seek`; использовались WASD/E/F7/Esc. Для диагностики временный `override.cfg` добавлял наблюдатель, читающий состояние и статическую сетку для выбора клавиш. Он не создаёт карту, не переключает сцены, не двигает персонажей и не изменяет часы. Та же схема наблюдения на неизменённом `main` воспроизводит ошибку, поэтому не скрывает порядок запуска.

Это реальная оконная игра с автоматическим управлением, **не ручное прохождение человеком**. Проверка в пользовательском редакторе Windows не выполнялась. Скриншоты сняты X11-захватом ffmpeg; видео — тот же захват, без подмены рендером сцены. Временный override после проверки удалён; его нет в коммите и штатной конфигурации.

## 9. Повторение проверок

Из корня репозитория:

```bash
python -B HutorReborn/tools/verify_runtime_fix_sources.py
python -B HutorReborn/tools/verify_project_layout.py
godot --headless --editor --path HutorReborn --quit
python -B HutorReborn/tools/verify_normal_startup.py --output /tmp/hutor-startup.json
godot --headless --path HutorReborn --script res://tests/verify_interior_content.gd
godot --headless --path HutorReborn --script res://tests/verify_worker_speed.gd
godot --headless --path HutorReborn --script res://tests/verify_door_transitions.gd
godot --headless --path HutorReborn --script res://tests/verify_daily_lifecycle.gd
godot --headless --path HutorReborn --script res://tests/verify_npc_day.gd
godot --headless --path HutorReborn --script res://tests/verify_npc_obstacles.gd
```

Для оконного повторения требуются Xorg/XTest, ffmpeg, одно окно игры и свежая выходная папка. `native_window_playtest.py launch --output /tmp/hutor-native` запускает обычную игру с read-only наблюдателем; в другом терминале `native_window_playtest.py door inn --output /tmp/hutor-native` выполняет вход/выход. Аналогично `elder`, `herbalist`, `woodcutter`, `old_man`, `storehouse`. Для NPC-сценария запустить `native_npc_scenarios.py --output /tmp/hutor-native` сразу после готовности новой игры, чтобы попасть в трактир до первого утреннего ухода. Остановить лаунчер созданием `/tmp/hutor-native/STOP`; он завершит свой процесс и уберёт только собственный неизменённый override. Существующий пользовательский `override.cfg` инструмент не перезаписывает. Параллельно штатный редактор в этой же папке не запускать.

Оставшиеся ограничения: нет ручной проверки в пользовательском Godot/Windows; не сопровождали визуально всех девятерых внутрь каждого дома в один вечер; не восстановлена отсутствующая локальная вложенная копия проекта; не исчерпаны все сочетания плотной толпы. Подтверждённых неустранённых ошибок в выполненных сценариях не осталось.
